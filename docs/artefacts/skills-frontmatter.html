A Skill Is Mostly Metadata

The conventions of the goblin-mode skills system: how a skill declares who invokes it, what it may touch, which model runs it and where its shared parts live. The body teaches Claude a job; the frontmatter decides whether that teaching ever fires. Written for Jason and for Jaz, who may nick any of it.

02 · Invocationthree shapes, decided by two booleans, and the law that binds them

man invocation

Everything else in the system hangs off this choice.

ShapeFrontmatterMeaningExample
commanddisable-model-invocation: trueOnly the user fires it. Its description never reaches Claude's listing, so it costs no context.pr-land, do-stud
dualdisable-model-invocation: false + a comment naming the gateClaude may fire it because it recognises the moment before the user does, and something irreversible is still gated.pr-update, roadmap-maintain
knowledgeuser-invocable: falseOnly Claude loads it; it is reference, not an action. Hidden from the / menu.clod-stack-svelte, the lens trio
The orchestration law

disable-model-invocation: true blocks the Skill tool mechanically, even when Claude is mid-way through executing a skill the user invoked. An orchestrator that says "invoke pr-create" dies at that line unless pr-create is dual-invocable. Every skill another skill calls must be invocable by the model; the sub-skill's own gate (or an auto token the orchestrator passes after running its own gate) does the protecting.

The when_to_use field is the agent's half of discovery: trigger phrases, orchestration edges, guardrails ("never invoke speculatively"). The description stays lean for humans scanning a menu. On command skills when_to_use reaches nobody at runtime and survives purely as maintainer documentation.

The inline hijack rule

Knowledge skills set neither model nor effort. Both fields override the session absolutely while the skill is active, and a reference skill loads inline into someone else's turn: an effort: low lens firing mid-design would sandbag exactly the thinking that summoned it. Command skills pin both fields because invoking one is choosing its workload; knowledge skills inherit because they ride along inside yours.

Glyphs live in metadata.glyph, never in the description text. Two retired conventions embedded triple Greek letters and runic pairs in descriptions; on sight, migrate. The metadata.family key carries the taxonomy the flat directory names cannot (personal skills get no directory namespacing), and tooling reads it: the skills README regenerates from frontmatter.

04 · Toolsevery grant scoped, every promise made mechanical

man tools

  • allowed-tools is mandatory on every skill and every rule in it is scoped. A bare Bash pre-approves the entire shell for the invoking turn; the audit found two and tightened both. Reference skills get reads; command skills get exactly the commands their steps run, with bundled scripts addressed through the same path in the rule and the body so they run unprompted.
  • disallowed-tools turns a prose promise into a mechanical one. "Reviews, never fixes" means banning Edit and Write; "pushes single tags only" means banning git push --tags. If the body promises restraint, the frontmatter enforces it.
  • Settings-level permission rules are the last resort, used only for a control frontmatter cannot express. The system currently needs none.
05 · Execution contextforking, path triggers, dynamic injection, and why there are no hooks

man execution

context: fork runs a skill in an isolated subagent, its body becoming the prompt. Fork eligibility is rare here by construction: most command skills carry approval gates or interviews, and a forked subagent can conduct neither. What does fork is the self-contained read-only investigation (agent: Explore keeps it honest); a fork that must write pins background: false, because backgrounded forks run a narrower tool set.

paths gates a knowledge skill's auto-loading behind file globs, and earns its place only when three conditions all hold: the skill is model-invocable, file identity is a reliable proxy for relevance, and no legitimate conversation-only trigger gets suppressed. Two skills pass (svelte, frontend-styler); four had globs quietly strangling their own advertised triggers, since "which database?" happens before any schema file exists.

Dynamic context, three preconditions

The !`command` injection runs before Claude sees anything, and a failed command aborts the whole invocation. So it demands: no dependence on arguments, no legitimate non-zero exit, output valid as a one-shot snapshot. The commit skills pass (git status cannot honestly fail); the roadmap skills fail on purpose, because their exit-code protocol is their graceful degradation and injection would turn it into a crash.

Hooks: none, anywhere. The tempting one (validate roadmaps.json after every edit) would fire during the deliberately inconsistent mid-flow state the workflow passes through. Validation belongs at the end of the flow, where the bodies already put it.

06 · The library layerthe namespace a flat directory can't give you, and the regeneration principle

ls ~/.claude/library/

Skills stay thin because the shared weight lives one level up. This is the namespace the flat skill directory cannot provide:

PathHoldsConsumers
references/shared methodology and conventions: roadmap-conventions.md, stud/methodology.mdwhole families point here instead of restating
scripts/deterministic halves: roadmap.py, branch-facts.sh, find-scaffold.sh, the drift hookskills judge; scripts compute
templates/fill-in skeletons: pr-description, READMEs, the roadmap dashboard HTMLoutput shape lives once
The regeneration principle

A generated file is never hand-edited: the skills README regenerates from frontmatter, the roadmap dashboard from roadmaps.json, the dependency diagram from the graph command. Hand-edits to projections get wiped by design, and a hardcoded file list in a script is rot waiting to happen; the audit found two already rotted.

One shared skill counts as shared infrastructure too: pr-review-dry_run holds the whole review methodology, and pr-review, branch-qa_review and the ship loop all call it rather than carrying thin copies that drift.

07 · Prose rulesno em-dashes, no Oxford commas, and a copy-ready skeleton

man prose

  • No em-dashes, anywhere: descriptions, bodies, comments, and the output formats skills generate. Colons, semicolons, commas or a restructure. The validator on posted PR reviews hard-fails on the whole dash family.
  • No Oxford commas. British spelling throughout, including generated projections.
  • Descriptions are third person, lead with the key use case, and carry no tags or tier markers; the combined description and when_to_use text truncates at 1,536 characters in Claude's listing.
  • Collapsible sections in any generated artefact default closed. The reader chooses what to expand; this page obliges.

cp skeleton.yaml ~/wherever/
