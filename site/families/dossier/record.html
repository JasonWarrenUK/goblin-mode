Everyone Gets a File

A skill that writes down what you learn about the people you work with, one durable fact at a time, into a private file per person. The point is compounding context: once the model knows who reads the handover, it stops writing for a generic reader. Most of the design is about the moments it should stay quiet.

I

Why It Exists

the payoff · the silence rule
01The Compounding Recordinferred

Every session starts knowing nothing about the people around the work. Ask for a handover document and you get one pitched at a reader with no name, no specialism and no habits, because that is all the model has. The output is fine and it is fine for nobody in particular.

The dossier is the correction. One gitignored file per colleague, holding what changes how work gets done: role and ownership, expertise and where it stops, standards they hold, what they reject, how they review. It accrues. The tenth fact costs the same to record as the first and is worth more, because it lands in a file that already has nine.

What Changes Downstream

The same request, twice

With no file. "Write the handover for the ingest work." Out comes a document that explains the whole service from first principles, defines every term once and picks its own idea of what matters.

With a file saying ravi owns ingest, is fluent in Go, is light on YAML anchors and reviews by running a branch before reading its diff. Out comes a document that skips the service tour, spells the anchor syntax out once and leads with the command that reproduces the failure.

Why it compounds Neither version took longer to produce. The difference is entirely in what was known before the first sentence, and the file is the only place that knowledge survives the end of a session.

Why a File Each

A paragraph in CLAUDE.md could hold the same words. It cannot hold four things this needs:

  • Dates. Every bullet carries the day it was recorded, so staleness is visible. A two-year-old claim about someone's expertise reads differently to last week's.
  • Correctability. One fact per bullet means a wrong one is deleted without disturbing its neighbours.
  • Marked inference. A prose paragraph flattens what someone said and what was guessed about them into the same register.
  • Absence. An ## Open questions section says what is not known, which is the part a paragraph silently omits.
What This Rests On

This is the thinnest evidence on the page. Five files exist and no output has been measured against one. The argument that a populated dossier improves a handover is reasoning from the design, and it is chipped inferred for that reason; dressing it up as a result would be the exact failure this page is meant to avoid.

02The Silence Rulerecorded

This skill is model-invocable, which means it fires by itself, in the middle of whatever the turn was about. That is the only way it can work. The moment worth catching is a claim about someone dropped in the middle of a sentence about something else, and by the time Jason thinks to write it down he has moved on. It also makes restraint the whole design problem. A skill that interrupts is worse than one that never runs, because the second is merely absent whilst the first is a tax on every sentence containing a name.

Fires on a durable attributeStays silent on
Role, seniority, ownershipRouting and tasking: "send it to Ravi"
Expertise and its limitsOne-off state: "on leave next week"
Preferences and standardsPassing mentions with no claim attached
What they care about, what they reject, how they reviewPeople Jason does not work with, unless he asks
How to work with them: pitch, handover, registerThird-party gossip about someone's character
Relationships between colleaguesAnything that will be false in a fortnight
Pronouns, when stated

The gossip exclusion is the one worth defending. A claim about someone's temperament, relayed second hand, is exactly the sort of thing that feels like useful context and is not a working fact. Recording it puts a stranger's judgement into a file that then shapes how everything gets written for that person.

The rule the skill states about itself

When it does not fire, do nothing and say nothing. A skill that announces its own restraint is worse than one that never ran.

Why it needs saying The obvious failure mode of an auto-firing skill is not wrongly recording things. It is narrating its own decision not to, once per name, forever.

When it does fire, the output is one line. No summary, no restating what was just said, then straight back to the actual task.

II

The File

frontmatter · shape · discipline · the gate
03Frontmatter, Line by Linerecorded

The real block, unedited, comments and all:

---
name: "Dossier: Record"
description: "Record a durable fact about a person Jason works with, in their own dossier file"
when_to_use: "Whenever Jason says something durable about a named person he works with: their role,
  expertise, preferences, what they care about, how they review or respond, how to work with them.
  Also when he introduces someone new, or asks for something about a person to be noted."
metadata:
  family: dossier
# No model or effort on purpose. This skill fires inline, mid-turn, inside
# whatever the session was already doing; both fields override the session
# absolutely while a skill is active, so setting either would downgrade the
# turn that triggered it.
disable-model-invocation: false # the trigger is a fact landing in conversation, which Claude
                                # sees before Jason thinks to record it; step 4 is the gate
user-invocable: true
allowed-tools: ["Read", "Glob", "Grep", "Write", "Edit"]
argument-hint: "[name] [what to record]"
---
FieldWhy it says that
description, when_to_useThese do reach the model here, unlike on a command skill. Model-invocable means the description is the trigger, so when_to_use is written as a list of the shapes a durable fact arrives in.
model, effortAbsent, and the comment explains why. Both override the session absolutely whilst a skill is active. A skill that fires mid-turn inside an Opus session would silently downgrade that turn to whatever it named. The only safe value for an inline skill is no value.
metadata.glyphAlso absent, and it follows from the row above. The glyph mirrors the model tier, so a skill with no model has no glyph, and the generated index shows an empty Model column for /dossier-record.
metadata.familydossier. It is what gives this page its indigo, under the one-hue-per-family rule the hub sets out.
disable-model-invocationfalse, which is the exception rather than the default. The house rule allows it when the trigger moment is one Claude sees before the user does and the skill carries its own approval gate. Both hold: a fact lands in conversation before Jason thinks to record it, and step 4 stops anything contested being written.
user-invocabletrue as well, so /dossier-record works when Jason wants to record something deliberately. Both doors open, which is unusual and correct here.
allowed-toolsRead, Glob, Grep, Write, Edit. No Bash at all, which is worth noticing on a skill whose step 2 shows an ls: the directory listing goes through Glob instead.

Compare the shape against its sibling in the red family, which is a command skill: that one pins model: opus and effort: high, carries a glyph, and sets disable-model-invocation: true because no document is self-evidently ready to be attacked. Same house rules, opposite answers, because one is a thing you ask for and the other is a thing that notices.

04What a File Looks Likerecorded

One file per person at library/profiles/dossier/{slug}.md, slug lowercase and matching the name they are called by. The schema lives in library/profiles/dossier/README.md, which is the one file in that directory that is tracked.

# Ravi

## Facts

- Owns the ingest service end to end. `2026-08-15`
- Fluent in Go, light on YAML anchors. `2026-08-15`
- Reviews by running the branch before reading its diff. `2026-08-15` *(inferred)*

## Working with them

- Lead a handover with the command that reproduces the failure.

## Open questions

- Do they want the migration plan in the PR or as a separate document?

Three sections, each doing a job the other two cannot.

  • Facts is what is true about them. Dated, one claim per bullet.
  • Working with them is what to do about it. The split matters because "light on YAML anchors" and "spell the anchor syntax out once" are separate claims, and the second can be wrong whilst the first stays right.
  • Open questions is what is not known. It is the section that makes the file work as a listening brief: a file with one fact and three open questions is doing its job, because it gives the next fact somewhere to land.

The Directory as It Stands

Five files hold twelve facts and eleven open questions between them. More questions than facts is what a young directory looks like, and it is the shape the schema is built to encourage: a file earns its place by naming what is missing, then fills in as the answers turn up.

Not one of those bullets carries *(inferred)*, which section 05 returns to.

05Disciplinerecorded

Five rules keep a file of this kind honest for longer than a month. Each one exists because of a specific way notes about people rot.

RuleThe rot it prevents
One fact per bulletA sentence carrying three claims can only be deleted whole. Splitting it means the wrong third can go without taking the right two thirds with it.
Dated, alwaysThe date marks when the claim was written down; it says nothing about when it became true. Without it there is no way to tell a current judgement from a first impression that has been sitting there for a year.
Mark inferenceA stated fact stands bare; anything worked out from context takes *(inferred)*. This matters most when the file is later used to predict how someone behaves, which is exactly what section 07 does with it.
Absolute dates in the text"Last week" is a fact with a shelf life of seven days. It becomes the date on the way in.
Pronouns only when statedunstated stays in the frontmatter until told otherwise, and everything written about that person uses they/them meanwhile. Guessing from a name is the failure mode, and it is one the file would then repeat in every document written for that person.
Provenance

Not one of the twelve bullets on disk carries *(inferred)*, and all five files still read pronouns: unstated. So two of the five rules have never done anything yet: nothing has been recorded that Jason did not say outright, and nobody has stated their pronouns for the frontmatter to change.

Why that is worth printing Four of the five files are timestamped 22:34 on 15 August 2026 and the skill file is timestamped 22:38. The files came first and the skill was written from them, so the discipline described here has mostly been applied by hand rather than by the flow it specifies.

06The Contradiction Gateunexercised

Step 4, and the only place the skill stops to ask. If a new fact contradicts a line already in the file, it writes neither version. It raises the conflict in one line, quotes both versions and asks which holds.

What that looks like

Conflict on ravi: file says "reviews by running the branch, not by reading the diff" 2026-08-15; you just said they read every line of the diff. Which holds?

The obvious implementation is to overwrite the old line, since the new information is newer. That loses the thing worth keeping. Somebody changing how they review is a fact in itself, and it is usually a more useful one than either of the two statements it sits between. Silently replacing the line records the outcome and destroys the event.

The gate is narrow on purpose. Additive facts need no permission at all, or the skill becomes a confirmation prompt attached to every conversation, which is the interruption tax section 02 exists to avoid. Conflicts alone.

Never Fired

Zero contradictions have been raised, because nothing recorded so far has contradicted anything else. The branch is written and untested, and it is the one most likely to need adjusting the first time it runs against something real.

III

Reach

the seam · privacy · surfaces · running it
07Facts and Modelsunexercised

This is where the two skills in this family meet, and the seam between them is the most carefully drawn line in either one.

/red-sabotage reviews a document as the colleague trying to kill it, aimed at one or two named readers. To do that it needs a reader model: nine fields covering what someone needs from a document, what they are protecting, what they can do to it, what they read, what they skip, what makes them reject it outright. Those models live in library/references/sabotage-personas.md.

A dossier file holds facts about a real person. A persona holds predictions about how that person behaves under review. When a persona slug matches a dossier file, red-sabotage derives what it can and interviews for the rest.

Which Fields Survive the Jump

Four of the nine come out of a dossier file cleanly, because they are restatements of things already recorded. Fluency comes out of noted expertise. Stake comes out of role and ownership. Needs comes out of their relationship to the work. Each derived field is printed with the line it came from, so a wrong derivation is visible before it is used.

The rest do not transfer, and the reason is that reading habits and how much slack someone cuts you only show up under pressure. Power, Reads, Skips, Charity and Verdict style are almost never written down about a colleague, because they are not the sort of thing anyone says out loud. Those get one short round of questions.

The line that split the two files

How someone reviews a document is inference about them. Their dossier holds facts. Keeping the review model in a separate file, labelled as a model and corrected there, is what stops a factual record about a colleague quietly filling with predictions about their temperament.

Why the direction matters A guess that gets written back into the facts file is indistinguishable from a fact within a week. One-way derivation is the only version of this that stays trustworthy.

Neither half of this has run. Red-sabotage has never been executed end to end, so the derivation path is specified and untested from both sides.

red family · the other half of this seam Bob Will Not Open the Deep Dive → /red-sabotage Adversarial document review aimed at one or two named readers. Nine persona fields, a stdlib slop scanner and a report ranked by which reader can do the most damage. Read it for what a persona is for.
08Privacy Architecturerecorded

These are notes about real people, held on one machine, and the whole directory is designed around that. The mechanism is two lines of .gitignore:

# Person dossiers stay local; the schema that documents them does not
/library/profiles/dossier/*
!/library/profiles/dossier/README.md

The contents never leave the machine. The schema is tracked, so the convention survives a fresh clone whilst none of the facts do. That split is the entire design: a future reader of the repo learns precisely how these files are shaped and nothing whatsoever about who is in them.

The Publishing Rule

The skill forbids copying dossier content into a tracked file, a commit message, a PR description, an artefact or anything published. The consequence is stated in the skill itself, and it is the sharpest sentence in the file:

From the skill's own rules

A guide written for a person is calibrated against their file; it never names them or quotes it.

What that buys The file can hold a sharp judgement, of the kind that would be awkward in a shared document, because the judgement only ever shows up as a better-aimed piece of writing.

This page is bound by that rule

ravi is invented. So is every fact attributed to them. This artefact is tracked and publishable, so it cannot name a single real person in the directory it describes, and every count in section 04 is an aggregate for the same reason.

The Test That Governs What Goes In

Two filters, and both are stricter than "is this true".

  • Working notes only. Record what changes how work gets done. Personal detail volunteered in passing stays out, however durable it happens to be.
  • Readable aloud. Anything in these files should be something Jason would be comfortable reading to the person it describes. A private file that could not survive being read back is a liability sitting on a laptop.
09Where It Surfacesrecorded

A file nobody opens is a diary. Three things read this directory, and the index is what makes the other two possible.

The Index Line

A new person gets one line in the People section of MEMORY.md, which is the file loaded into context at the start of every session:

- **Ravi**: owns the ingest service, reviews by running it, [dossier](../../../../library/profiles/dossier/ravi.md)

The full facts stay in the file. The index carries a name and a hook, which is enough for recall to decide the file is worth opening. Existing people need no index change unless the hook itself has gone wrong, so the index stays short as the files get long.

ReaderWhat it takes
/dossier-recordWrites and updates. The only writer.
/red-sabotageDerives a review profile when a persona slug matches a file. Writes to the persona store; never back here.
MEMORY.mdHolds one pointer line per person, so recall can find the file at all.
Anything writing for a personA handover, a pitch, a PR description aimed at a named reviewer. This is the intended payoff and the one with no measurement behind it yet.
10Run Itunexercised

Three Ways In

# the usual one: say it, and the skill fires by itself
"Ravi owns the ingest service now"
→ Recorded: ravi owns the ingest service → library/profiles/dossier/ravi.md

# deliberate, with the fact on the line
/dossier-record ravi reviews by running the branch rather than reading the diff

# deliberate, no argument: asks who and what
/dossier-record

What Comes Back

One line, then the turn carries on with whatever it was about. No summary, no restatement, no offer to record anything else.

Near misses

A slug that nearly matches an existing file (ravinder against ravi, a nickname, a surname) stops and asks which person is meant. Two files for one person is the failure that makes the whole directory untrustworthy, and it is the one mistake here that cannot be fixed by deleting a bullet.
