Metadata Is Whatever I Say It Is

The harness parses a fixed set of frontmatter fields and ignores everything else. metadata is everything else. No schema defines it, no validator checks it and no error fires when a value is wrong, which makes it a free namespace and an unpoliced one at the same time.

I

What Exists

two props, both mine
01The Block Nothing Readsin use

A SKILL.md frontmatter carries fields the harness knows: name, description, when_to_use, model, effort, allowed-tools, disable-model-invocation, user-invocable, argument-hint. Those have meanings that were decided elsewhere, and using them wrong changes how a skill behaves.

metadata is not one of them. It parses as YAML, it sits in the file, and nothing upstream looks at it. The model never sees it. No schema constrains its shape. A typo in a key produces no error anywhere.

What that buys, and what it costs

The block is a namespace nobody else has a claim on, so any convention invented there is free and immediately available across all 52 skills. It is also completely unchecked, so a value can be wrong for a year and the only symptom is a table quietly telling you something untrue.

Both halves are load-bearing. The freedom is why family could be invented in an afternoon and wired into three separate tools. The absence of checking is why the second prop, glyph, is the one that can lie.

02metadata.familyworked

One line per skill, naming the group it belongs to. All 52 skills carry one, across 19 distinct values.

metadata:
  family: dossier

The flat skills/ directory cannot express this on its own. Personal skills get no directory namespacing, so the only grouping available in the filename is a prefix convention, and a prefix convention breaks the moment a skill belongs to a family whose name is not its first word.

Declaring family: red on a single skill is the interesting case. It costs nothing now and it reserves the namespace, so red-steelman can arrive later without renaming anything. A taxonomy that only appears once a group is crowded is a taxonomy applied retroactively, which is when renames happen.

03metadata.glyphin use

A rune standing for the model tier the skill pins. The generated index renders it as a column.

GlyphRuneModelTypical work
ᚺhagalazhaikuscript wrappers, mechanical projections
ᛊsowilosonnetbounded judgement: prose, wiring, validator-gated edits
ᛟothalaopusreview verdicts, graph rationality, greenfield decomposition
ᚠfehufableunattended long-horizon loops (next-task-ship, nothing else)

Glyphs live here and never in the description text. Two retired conventions embedded triple Greek letters and runic pairs in descriptions; on sight, migrate.

This one can lie

The glyph restates model:, which is two lines above it in the same file. Nothing reconciles the two. A skill can say model: opus and glyph: ᚺ and the index will happily print a haiku rune next to it forever, because the index reads the glyph and not the model.

A knowledge skill pins no model, so it carries no glyph, and the generated index shows an empty column for it. That part is consistent. The failure mode is narrower and worse: a duplicated value with no reconciliation, in a table nobody re-checks after the first read.

It survives because the runes are good and the index reads better with them. It is worth keeping the cost in view rather than pretending the field is free, and it is the reason section 05 has a rule at all.

04One Hue per Familyworked

The fullest thing family currently drives, and a worked example of a metadata prop earning its place.

Every page on this site keys its palette to the family of the skill it documents. Layout is shared and lives in one stylesheet; the hue is the only thing that varies, and it varies for a reason. Landing on a page mid-scroll, the colour says which family you are in before the title does, and the URL says it too.

FamilyHuesReading
configamber, emeraldInherited from the first page written in this family
redred, teal, cinnamonA marking pen on a document somebody wants dead
dossierindigo, violet, greyInk in a ledger; violet for inference, grey for what stays private
the indexgrey onlyNo family, so no hue

All hues come from Reasonable Colors, which is fixed. Which hues a family gets, and what each one means inside a page, gets decided once when that family's first explainer is written, then documented as mapping notes at the top of that page's stylesheet. The second page in a family reads those notes instead of re-deciding.

Why this is the good example

Nothing in a skill file implies a colour. The value could not be derived, something running consumes it, and a wrong value is visible immediately because the page comes out the wrong colour. Those three properties are what section 05 turns into a test.

What Else It Could Hold

a draft, not a decision
05The Test for Adding Oneproposed

Two props in and one of them already has a defect. Three questions, drawn from what separates family from glyph:

Questionfamilyglyph
Could it be derived from the file? If yes, deriving it is free and storing it invites drift.No. Nothing in a skill file implies its family.Yes. It restates model:.
Does anything running read it? A prop nothing consumes is a comment with extra steps.Three readers.One reader.
Is a wrong value visible? With no validator, the only check is whether the mistake shows up somewhere.Yes. The page comes out the wrong colour.No. The index prints the wrong rune indefinitely.

A prop answering no, yes, yes is worth adding. glyph answers yes, yes, no, which is the exact profile of a field that will eventually be wrong.

There is a fourth consideration that is not a test so much as a warning. Every prop added here is a promise to maintain it by hand across 52 files, with nothing to remind you. A convention that is only half applied is worse than one that was never started, because a partial field reads as an absent value rather than an unfilled one.

06Candidatesproposed

Six, ranked by friction they would remove today rather than by how clever they are. Nothing below is written into a skill file yet.

PropWhat it fixes now
exercised: falseTwo explainer pages hand-write "never run end to end", in a statline and again in prose. The drift is already possible. One value would generate the card, the chip and the statline.
reads: / writes:Declared file dependencies. red-sabotage reads the persona store and the dossier; dossier-record writes the dossier. At 52 skills, "what breaks if I move this library file" is currently a grep and a hope.
pairs_with:The red and dossier seam is written out three times across this site. One edge would generate all three, and stop one surface going stale whilst the others stay right.
surface:Where output lands: terminal, docs/artefacts, site/, GitHub. Answers "which skills can publish something publicly", which is exactly what site/CLAUDE.md exists to worry about.
status:stable, provisional, retired. Two retired conventions are already mentioned on the frontmatter page as things to migrate on sight, which currently means somebody has to remember them.
since:The date a skill arrived. Gives the set a real changelog and lets this site badge recent additions.

Against the Test

All six answer no to derivability, which is the point: none of them can be worked out by reading the file. exercised, surface and pairs_with would be visible when wrong, because a page or a link would come out incorrect. status and since would not be, which puts them in the same category as glyph and is worth deciding deliberately rather than by accident.

Draft status

This section is a first pass and has not been through a cull. The ranking is mine, the framing is mine, and none of it has survived contact with the fifty-two files it would have to be applied to.
