Three skills that share one script and one config, built from nothing. The docsuite family generates a doc set, edits one file inside it, then patches the rest back into line. Everything here is copy-ready; the point is to have it working on your own machine by the end.

01What You'll Have Built

man tutorial

Everything above described the rules. This section is the exercise. If the SKILL.md files you've written so far are prose with a name and description at the top and nothing else, that's the starting point this assumes: no YAML beyond the two required keys, no scripts, no shared files, one skill that stands entirely alone. By the end you'll have three skills that genuinely depend on each other, a script that does the counting so the model doesn't have to, and a config file that all three read from and none of them hardcodes.

The worked topic is a documentation-maintenance suite, docsuite-*: a family that drafts, edits and syncs a project's own docs (README, architecture notes, whatever the project defines) against the actual codebase. Not this repo's own doc-* family, which does something adjacent; a fresh build so every file below is something you can create, read in full, and understand end to end. That completeness is the point. Nothing here is elided for space in a way that would leave a gap in your working copy.

The shape, before the detail

Three command skills, one shared script, one shared config, and a set of per-type reference files loaded on demand. docsuite-draft [doc-type] writes or rewrites a doc from scratch. docsuite-edit [doc-type] [edit-kind] makes a targeted change to a doc that already exists. docsuite-sync [doc-type] finds where a doc has drifted from the code and patches only the drifted spans. All three take doc-type as an argument rather than existing once per type, because the type selects which config entry and which reference file to load, not which skill to invoke. That argument-driven selection is the more useful pattern to learn than one skill per type would have been.

Step 1 · the shared config

Before You Start

You need jq on the path, a repo with at least one doc worth maintaining, and somewhere to put three skill directories. Nothing else. The whole build is four files you write by hand plus one reference file per doc type.

You are done when docsuite-sync readme runs against a repo, prints a drift report it computed rather than guessed, and patches only the spans that drifted. If it rewrites the whole file, something in the chain is wrong and section 09 is where to look.

02The Shared Config

Before any skill exists, decide what "correct" means for each doc type, once, in a file every skill will read. This is the source of truth: which sections a README must carry, who it's written for, and the same for every other doc type the project cares about. Nothing below hardcodes a section list inline; everything points here instead.

write docs.config.json

{
  "readme": {
    "audience": "a developer cloning this repo for the first time",
    "sections": ["setup", "usage", "configuration", "license"],
    "tracks": ["package.json", "src/**/*.ts"]
  },
  "architecture": {
    "audience": "a maintainer who hasn't touched this module in six months",
    "sections": ["modules", "data-flow", "external-dependencies"],
    "tracks": ["src/**/*.ts", "src/**/index.ts"]
  }
}

Each entry's tracks array is what the sync script below actually diffs against; sections and audience are what the drafting and editing skills read. One file, three consumers, no duplication.

Step 2 · the shared script, the deterministic half

The reason this is a file rather than three copies of a section list is what happens when the answer changes. Decide that every README needs a troubleshooting section and you edit one array; all three skills pick it up on their next run because none of them ever knew the old list. Three skills with the list inline would need three edits, and the one you forgot would keep passing its own check.

Adding a doc type is the same trade. One new entry here, one new reference file, and every skill handles it without being touched, because the type is an argument rather than a branch in the prose. That is the property worth protecting as the suite grows.

Each tracks entry is a shell glob, matched by compgen -G in the script below. src/**/*.ts asks "do any TypeScript files still exist under src", not "does this exact path exist", which is what makes it survive ordinary refactors and still fire when a whole area is deleted.

03The Shared Script

The question "has this doc gone stale" has an objective answer: does the file list in tracks still match what's actually in the tree, do the section headings in the doc still match sections, has anything changed since the doc's own last-modified time. None of that needs a model's judgement to compute; it needs find, a bit of jq, and a stat call. So it lives in a script, not in a skill's prose, and every skill below calls the same one rather than re-deriving the facts itself.

write ~/.claude/library/scripts/doc-sync.sh

#!/usr/bin/env bash
# doc-sync.sh <doc-type>: diffs docs.config.json's claims for <doc-type>
# against actual repo state and emits one JSON drift report.
# Computes; does not judge. The calling skill's prose decides what to do
# with what this finds.
set -euo pipefail
doc_type="$1"
config=$(jq -r --arg t "$doc_type" '.[$t]' docs.config.json)

# tracked-file existence: does every path in "tracks" still resolve?
missing_tracks=$(echo "$config" | jq -r '.tracks[]' | while read -r pattern; do
  compgen -G "$pattern" >/dev/null || echo "$pattern"
done)

# section coverage: which required sections are absent from the doc itself?
doc_path="$doc_type.md"   # simplified; a real script maps type -> path
missing_sections=$(echo "$config" | jq -r '.sections[]' | while read -r s; do
  grep -qi "^#.*$s" "$doc_path" 2>/dev/null || echo "$s"
done)

# a newline-separated string becomes a JSON array; the select drops the
# empty line printf leaves behind when nothing drifted, so "clean" is [] not [""]
to_json() { printf '%s
' "$1" | jq -R . | jq -s 'map(select(length > 0))'; }

jq -n \
  --arg     doc_type         "$doc_type" \
  --argjson missing_tracks   "$(to_json "$missing_tracks")" \
  --argjson missing_sections "$(to_json "$missing_sections")" \
  '{doc_type: $doc_type, missing_tracks: $missing_tracks, missing_sections: $missing_sections}'

This is the same split as branch-facts.sh elsewhere on this page: the script emits exact numbers and exact lists, and the skill that calls it judges what to do with them. Nobody's making the model count files by reading a directory listing into context; it reads one JSON object instead.

Step 3 · per-type reference files, loaded on demand

The Output Contract

One JSON object, three keys, every time:

{ "doc_type": "readme", "missing_tracks": [], "missing_sections": ["configuration"] }

Two empty arrays means clean. That contract is the entire interface between the deterministic half and the judging half, and it is why all three skills can call the same script and do completely different things with the answer. The script never says "you should add a configuration section"; it says the heading is absent, and the skill decides.

set -euo pipefail matters more here than in most scripts. A malformed docs.config.json should stop the run with a non-zero exit rather than emit a report claiming nothing drifted, because a silent empty report is indistinguishable from a clean one to whatever reads it next.

One correction since first publication

The emitter here previously carried two unterminated command substitutions and read $ENV.doc_type, which is unset unless exported. It failed with invalid JSON text passed to --argjson. The version above was run before this page was republished. The select(length > 0) is a second fix: without it, a clean run returns [""] rather than [], and every consumer has to special-case a list containing one empty string.

04The Reference Files

A README and an architecture doc want different things from the model writing them: a README wants concision and a working quickstart; an architecture doc wants module boundaries and honesty about what's still coupled. Rather than folding both sets of guidance into every skill's body (paid for on every invocation, whichever type is being written), each type gets its own file, and the skill loads only the one the argument selected.

FileLoaded when
library/references/doc-types/readme.mddoc-type = readme
library/references/doc-types/architecture.mddoc-type = architecture

This is the same instinct behind this repo's own split-file skills, which break a large body into on-demand sibling files rather than one long inline block, but selected by an argument's value instead of by which section the reader happens to need next.

Step 4 · docsuite-draft, the full write

The filename is the argument. docsuite-draft architecture loads doc-types/architecture.md with no lookup table and no case statement anywhere, so adding a type means adding a file rather than editing a skill. A mapping that lives in a naming convention cannot drift out of sync with itself.

Loading on demand is the other half. A reference file per type, read only when that type is the argument, keeps the skill's own body short and keeps four types' worth of voice guidance out of a run that only needed one. The cost is that a missing reference file is a runtime surprise rather than a startup error, which is drill three in section 09.

05docsuite-draft

write ~/.claude/skills/docsuite-draft/SKILL.md

---
name: "Docsuite: Draft"
description: "Write or fully rewrite a project
  doc from its config entry"
when_to_use: "When a doc-type in docs.config.json
  has no file yet, or the existing one is thin
  enough that a rewrite beats an edit."
model: sonnet
effort: medium
metadata:
  glyph: ᛊ
  family: docsuite
disable-model-invocation: true
allowed-tools: ["Read", "Write",
  "Bash(~/.claude/library/scripts/doc-sync.sh:*)"]
arguments: ["doc-type"]
argument-hint: "[readme|architecture]"
---

1. Read the $doc-type entry from docs.config.json
   for its audience and required sections.
2. Load the matching reference file at
   ~/.claude/library/references/doc-types/$doc-type.md
   for type-specific voice and shape.
3. Run "$HOME"/.claude/library/scripts/doc-sync.sh $doc-type
   to get the objective drift report.
4. Write the doc for the stated audience, in every
   required section. Every path in the report's
   missing_tracks must be reflected somewhere in
   the doc or the section it belongs to must be
   explicitly marked TODO, never silently dropped.
disable-model-invocation: true because a full rewrite is destructive to whatever's there; this one stays user-only, unlike the two below.
allowed-tools scopes Bash to exactly one script, not the shell. Read and Write are ungated here because writing the doc is the whole job.
arguments carries only doc-type; the body's step 1 is what turns that one argument into a config lookup, a file path and a script call.
step 4's rule is the accountability clause: the script's findings can't be quietly ignored by the prose that follows it.

The four steps run in that order for a reason. Config first, because it names the audience every later decision serves. Reference file second, because voice shapes how the sections get written rather than which ones exist. Script third, so the drift report is in hand before a single word is drafted. Writing first and checking afterwards produces a doc you then have to argue with.

Write rather than Edit is the honest grant here: this skill replaces a file wholesale, and pretending otherwise with a narrower tool would mean the prose and the permissions disagree. Its sibling in section 06 grants the opposite, for the opposite reason.

06docsuite-edit

Drafting from scratch is the easy skill to picture; the other two earn their keep once a doc already exists and most of it is fine.

docsuite-edit, the surgical change

Rewriting a whole README to add one missing section, or to shift its tone for a new audience, throws away everything that was already right. docsuite-edit takes a second argument naming the kind of change, and only touches what that change implies.

---
name: "Docsuite: Edit"
description: "Make a targeted change to an
  existing project doc"
when_to_use: "When the doc exists and is mostly
  right: adding one section, retheming its tone,
  or restructuring for a different audience."
model: sonnet
effort: medium
metadata:
  glyph: ᛊ
  family: docsuite
disable-model-invocation: false # invocable:
  Claude may recognise "add a section on X to the
  README" as this skill before the user names it
allowed-tools: ["Read", "Edit",
  "Bash(~/.claude/library/scripts/doc-sync.sh:*)"]
arguments: ["doc-type", "edit-kind"]
argument-hint: "[readme|architecture]
  [add-section|retheme|restructure]"
---

1. Run "$HOME"/.claude/library/scripts/doc-sync.sh $doc-type
   first, even for a small edit: an edit that ignores
   drift can make the doc more wrong, not less.
2. Read the existing doc and the $doc-type config
   entry.
3. Apply exactly the change $edit-kind names.
   add-section only adds; retheme only
   changes voice, never structure; restructure only
   reorders, never rewrites sentences that don't move.
allowed-tools carries Edit, not Write. This skill changes an existing file in place; it never creates or replaces one wholesale, and the tool grant says so mechanically rather than trusting the prose alone.
dmi: false, with a rationale comment. Unlike docsuite-draft, an edit is bounded enough that Claude recognising the moment ("add a section on deployment") is safe: nothing here is as destructive as a full rewrite.
step 3's three-way split is what keeps $edit-kind from becoming a vague "make it better": each value is a promise about what will and won't change.

docsuite-sync, the patch-only fix

The second argument is an enum rather than free text because an unbounded $edit-kind collapses into "improve the doc", which is the same as a rewrite with extra steps. Three named values each carry a promise about what will not change, and a promise is checkable in a way that an instruction is not.

07docsuite-sync

This is the one worth the closest look, because it's the clearest example on this page of token-efficient, script-driven correction rather than full regeneration. It doesn't rewrite the doc and it doesn't ask a human what changed; it runs the script, and for every drifted item the script names, it patches exactly that span and nothing else.

---
name: "Docsuite: Sync"
description: "Patch a doc's stale, mechanically
  checkable claims against current repo state"
when_to_use: "Periodically, or after a change
  that might have invalidated a doc's file lists or
  section coverage, before reaching for a full edit."
model: haiku
effort: low
metadata:
  glyph: ᚺ
  family: docsuite
disable-model-invocation: false # invocable:
  read-only diagnosis until step 2's patch, which is
  narrow enough to need no separate gate
allowed-tools: ["Read", "Edit",
  "Bash(~/.claude/library/scripts/doc-sync.sh:*)"]
disallowed-tools: ["Write"] # patches
  spans; never replaces the file
arguments: ["doc-type"]
argument-hint: "[readme|architecture]"
---

1. Run "$HOME"/.claude/library/scripts/doc-sync.sh $doc-type.
   If both missing_tracks and missing_sections
   are empty, stop and report the doc clean; read
   nothing further.
2. For each entry in missing_tracks, find and patch
   only the line or list that names it. For each
   entry in missing_sections, add only that
   section's heading and a one-line stub, never
   rewrite a section that wasn't named.
3. Never touch a paragraph the report didn't flag.
haiku, low effort. Named-span patching from a JSON list is mechanical work; nothing here needs sonnet's judgement, which is exactly the deterministic-half payoff, a script cheap enough to run often and a model tier cheap enough to match it.
disallowed-tools bans Write mechanically, backing up step 3's prose promise the same way pr-review-dry_run's ban on Edit backs up "reviews, never fixes" elsewhere on this page.
step 1's early exit is the token-efficiency payoff made concrete: a clean doc costs one script call and nothing else, never a full read of the file.

The early exit is the part to copy into your own skills. A run that finds two empty arrays should cost almost nothing: no doc read, no model reasoning, no output beyond saying it was clean. Skills that always do the expensive thing regardless of what the cheap check found are where most of the waste in a skill library lives.

08Wiring It Together

docsuite-draft readme

Trace one call all the way through, because this is where the three skills stop being three independent files and become a system. docsuite-draft readme reads docs.config.json's readme entry for audience and sections; loads library/references/doc-types/readme.md for voice; runs doc-sync.sh readme for the objective drift report; writes the doc, accounting for every item that script found. Three months later, someone runs docsuite-sync readme after a refactor: the script notices a file in tracks no longer exists, and the skill patches the one sentence that named it, nothing else. Later still, someone runs docsuite-edit readme add-section to document a new deployment step: it re-checks drift first, then adds exactly that section.

One shared config, one shared script, three skills that each do a genuinely different job with them. That's the whole pattern: not three skills that happen to share a topic, three skills that would each be worse alone.

FileRole
docs.config.jsonshared config: audience + sections + tracked paths, per doc-type
library/scripts/doc-sync.shshared script: the deterministic half, called by all three skills
library/references/doc-types/*.mdper-type voice and shape, loaded on demand by the doc-type argument
skills/docsuite-draft/SKILL.mdfull write, user-only, dmi: true
skills/docsuite-edit/SKILL.mdtargeted change, dual-invocable
skills/docsuite-sync/SKILL.mdpatch-only fix, dual-invocable, haiku
09Break It on Purpose

Nothing on this page is load-bearing until you have watched it fail. Four drills, each one aimed at a different link in the chain, and each with a specific right answer.

Drill One: Delete Something Tracked

Remove a file that tracks matches, or point a glob at a directory you have just renamed, then run the script alone. It should name that pattern in missing_tracks and say nothing else. If it reports a section problem too, your doc_path mapping is wrong rather than your config.

Drill Two: Break the Config

Put a trailing comma in docs.config.json and run docsuite-sync readme. The correct outcome is a non-zero exit and no report. If you get a report claiming nothing drifted, set -euo pipefail is missing or a pipeline is swallowing the failure, and every skill downstream is now being told the doc is fine.

Drill Three: Ask for a Type That Has No Reference File

Add a changelog entry to the config, write no doc-types/changelog.md, then draft it. Step 2 fails to load a file that does not exist. Decide deliberately whether that should stop the run or fall back to a default voice, then write the answer into the skill body. This is the cost of the naming-convention lookup, and it is worth paying with your eyes open.

Drill Four: Give Edit a Kind It Does Not Know

Run docsuite-edit readme make-it-punchier. The skill should refuse rather than improvise, because the enum is the whole guarantee. If it cheerfully rewrites your README, step 3's three-way split is prose the model read as a suggestion, and it needs to be written as a constraint.

The habit this is teaching

When the output looks wrong, read the script's JSON before you touch the skill. The script is deterministic and the prose is not, so the JSON is either right or obviously broken, and it tells you which half of the system to fix. Debugging the skill first is how an afternoon disappears.
